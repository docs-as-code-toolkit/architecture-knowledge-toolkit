[[architecture-metamodel]]
== Architecture Metamodel

The architecture metamodel is part of the solution strategy. It defines the
small set of metadata fields and relationship types used by this repository. It
keeps architecture knowledge reviewable as source text while still enabling
deterministic generated views.

The model is intentionally simple. Teams can add domain-specific conventions on
top, but the shared core should remain stable, explicit, and easy to validate.

=== Source of Truth

AsciiDoc files are the primary authoring format. Metadata is stored as YAML front
matter at the top of each architecture artifact.

[source,yaml]
----
id: ADR-001-use-kafka
type: ADR
title: Use Kafka as the event backbone
status: accepted
owner: platform-architecture
created: 2026-06-25
reviewed: true
derived_from:
  - type: question
    description: Should this application offer an open REST API?
    anchor: q-arch-001
tags:
  - events
relations:
  - type: addresses
    target: QS-001-event-processing-latency
    status: accepted
    rationale: Kafka supports partitioned processing for latency-sensitive flows.
----

The repository owns the truth. AI-generated metadata or prose is only a
suggestion until a reviewer accepts it.

=== Common Artifact Metadata

[cols="1,1,3", options="header"]
|===
| Field | Required | Meaning

| `id`
| yes
| Stable artifact identifier. It must not be reused after deletion or rename.

| `type`
| yes
| Artifact type from the supported type list.

| `title`
| yes
| Human-readable artifact title.

| `status`
| yes
| Review state of the artifact. See xref:artifact-lifecycle-status[] for the defined values and for the separate validity axis.

| `owner`
| yes
| Person, team, or role accountable for the artifact.

| `created`
| yes
| Creation date in `YYYY-MM-DD` format.

| `updated`
| no
| Last meaningful update date in `YYYY-MM-DD` format.

| `reviewed`
| no
| `true` only after human review. AI suggestions should start as `false`.

| `generated`
| no
| `true` only for derived output. Source artifacts should normally be `false`.

| `summary`
| no
| Short summary suitable for indexes and generated overview pages.

| `derived_from`
| no
| Optional provenance for why the artifact was created, for example an input
question, external document, repository path, URL, conversation note, or source
artifact. Use this for origin information; use `relations` for architecture
traceability between artifacts.

| `tags`
| no
| Lowercase tags for grouping and filtering.

| `relations`
| no
| Explicit outgoing relationships to other artifacts.
|===

=== Supported Artifact Types

[cols="1,3", options="header"]
|===
| Type | Use

| `ADR`
| Architecture Decision Record. Captures a decision, considered options, and consequences.

| `QualityScenario`
| Concrete, measurable quality requirement or scenario.

| `Risk`
| Architecture risk with cause, event, impact, assessment, and mitigation options.

| `Requirement`
| Functional or non-functional requirement referenced by architecture work.

| `Constraint`
| Binding technical, organizational, legal, or operational limitation.

| `Component`
| Architecture building block or deployable element.

| `Interface`
| Contract or integration point between components or systems.

| `Stakeholder`
| Person, role, organization, or group with architecture concerns.

| `Concept`
| Reusable architecture concept, pattern, or definition.

| `Document`
| Supporting documentation that participates in traceability.
|===

[[artifact-lifecycle-status]]
=== Artifact Lifecycle Status

An artifact carries two lifecycle axes. `status` answers how confirmed the
artifact is, and `validity` answers whether it still holds. Both can be true at
once: an accepted risk that has been mitigated away is `status: accepted` and
`validity: retired`. Keeping the axes apart is decided in
xref:adr-009-artifact-retirement-and-relation-validity[].

The separation is not complete yet. `superseded` and `deprecated` are temporal
statements that still sit on the review axis, and ADR-009 deliberately left
them there instead of migrating them with the same decision, because that
migration overlaps with deriving `superseded_by` from an outgoing `supersedes`
relation. Read them as transitional values: every other `status` value is a
review verdict, and new temporal information belongs on `validity`.

`status` is the review axis, apart from those two transitional values.

[cols="1,3", options="header"]
|===
| Status | Meaning

| `draft`
| Work in progress. Incomplete notes or an artifact that is not yet a coherent
proposal. Not architecture truth.

| `proposed`
| Complete enough to review, but not reviewed. AI-created artifacts start here.

| `reviewed`
| A human has checked the content without deciding to adopt it.

| `accepted`
| Adopted as the repository's architecture knowledge. Only reachable through
human review. For a `Risk` artifact this means the risk description is accepted
knowledge, not that the risk itself is deliberately carried; that belongs in the
risk's own acceptance section.

| `rejected`
| Considered and intentionally not adopted. The artifact stays in the repository
as the record of an option that was turned down.

| `superseded`
| Transitional, temporal. Replaced by a newer artifact, which is named in
`superseded_by`. The newer artifact carries the `supersedes` relation.

| `deprecated`
| Transitional, temporal. Still in force, but discouraged for new work. Use it
where something is being phased out and can still be encountered, such as a
component, an interface, or a concept. Do not use it for an artifact whose
subject no longer exists at all; that is retirement on the validity axis.
|===

`validity` is the temporal axis. It is optional, and an absent value means
`active`. Validator and generator implement that reading explicitly; a schema
`default` is an annotation and materializes nothing.

[cols="1,3", options="header"]
|===
| Validity | Meaning

| `active`
| The artifact still holds. This includes a risk that the team knowingly
carries: a deliberately accepted residual risk is still present, so it stays
active and records its acceptance in the risk artifact.

| `retired`
| The artifact's subject no longer exists or no longer applies. The artifact
stays in the repository with its stable ID and its review status.
|===

A retired artifact records when and why:

[cols="1,3", options="header"]
|===
| Field | Meaning

| `retired_on`
| Date of retirement, on or after `created`.

| `retired_reason`
| Machine-readable reason, for filtering and generated views.
`no-longer-applicable` and `removed` apply to every artifact type. `Risk`
artifacts add `mitigated` and `materialized`.

| `retired_note`
| Free text that explains the retirement to a human reader. The reason is for
machines, the note is for people; neither replaces the other.
|===

The three fields belong to retirement and are absent while an artifact is
active.

Retirement never rewrites the relations that touch the artifact. A relation
keeps the relationship status it was reviewed with, because it stated something
that was true when it was made. `rejected` is a verdict about the claim itself,
for example that a decision never mitigated the risk it named, and not a way to
express that time has passed.

A relation is inactive for the current architecture when either endpoint is
retired, not only its target. Generated impact and traceability matrices keep
rendering an inactive relation and mark it with `(inactive)` in the relation
type cell, carrying the `relation-inactive` role so a renderer can style it.
Authoring a new relation to a retired artifact stays allowed, because a
historical link such as `documents` or `supersedes` is legitimate; the
validator warns about it so an accidental reference to obsolete knowledge
becomes visible.

=== Relationship Types and Semantics

Relationships are directed: `source --type--> target`. Relationship semantics
should be read from the source artifact toward the target artifact.

`derived_from` is not a relationship type. It records provenance for review and
navigation when an artifact originated from a question, prompt, external source,
or source document. If the origin is itself an architecture artifact and the
connection has architectural meaning, also model the architectural connection as
an explicit relation.

Generators may expose selected metadata as AsciiDoc attributes in derived
per-artifact fragments, for example `:derived_from_description:`. Source
documents can include those fragments before conditional prose that needs model
values:

[source,asciidoc]
----
\include::generated/adr-000-short-title-attributes.adoc[]

\ifdef::derived_from_description[]
{derived_from_description}
\endif::[]
----

Generators also derive per-artifact impact and traceability matrix fragments
from metadata relations. Source artifacts keep the visible `=== Impact` and
`=== Traceability` section headings and include the generated fragments with
`leveloffset=+2`, because the generated fragments begin with `== Matrix` and
the including source document owns the semantic section heading.

[cols="1,3", options="header"]
|===
| Relationship | Semantics

| `addresses`
| The source responds to, satisfies, or intentionally handles the target.

| `depends_on`
| The source requires the target to remain valid or implementable.

| `constrains`
| The source limits the design space of the target.

| `refines`
| The source adds detail to the target without replacing it.

| `supersedes`
| The source replaces the target as the current artifact.

| `conflicts_with`
| The source is in tension with the target and needs explicit resolution.

| `mitigates`
| The source reduces the likelihood or impact of the target risk.

| `introduces_risk`
| The source creates or increases the target risk.

| `affects`
| The source has a meaningful impact on the target, but no stronger relation applies.

| `verifies`
| The source provides evidence that the target is satisfied.

| `documents`
| The source documents, explains, or records the target.

| `relates_to`
| Weak relation for early capture. Prefer a more specific type after review.
|===

=== Relationship Status

[cols="1,3", options="header"]
|===
| Status | Meaning

| `proposed`
| Suggested but not reviewed. AI-generated relations should start here.

| `reviewed`
| Checked by a human but not necessarily accepted as architecture truth.

| `accepted`
| Accepted as part of the repository's architecture knowledge.

| `rejected`
| Considered and intentionally rejected.
|===

=== Extension Rules

* Add new artifact types only when existing types are insufficient.
* Add new relationship types only when the semantics cannot be expressed clearly
  with an existing type.
* Keep generated fields out of source metadata unless they are explicit inputs.
* Preserve stable IDs even when titles or filenames change.
* Prefer explicit relation metadata over inferred links in prose.
